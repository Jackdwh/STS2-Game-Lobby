# restart-trace-v1 重开诊断版

这是定位桌面房主“设置 → 房间管理 → 重开一局”原生崩溃的**诊断版，不是修复版**。内部 mod 版本号暂仍为 0.6.3；启动日志会额外显示：

```text
sts2_lan_connect diagnostic build: restart-trace-v1; restart tracing only, not a crash fix.
```

## 记录范围

仅在自动重开尝试接管续局页面的同步调用期间启用：

- 续局存档的模式、是否自定义、进阶等级，以及网络服务类型/平台/连接状态。
- 获取载入页面、`InitializeAsHost`、`stack.Push` 前后的检查点。
- `NMultiplayerLoadGameScreen` 的初始化、`AfterMultiplayerStarted`、`OnSubmenuOpened`。
- `NAscensionPanel` 的初始化、模式切换、火焰样式、最大进阶、进阶等级、文字和箭头刷新。
- 上述方法参数的标量值、相关字段是否为空、Godot 对象是否有效。
- 如果出现可捕获的异常，记录现有诊断脱敏器生成的类型、堆栈和指纹，然后保持原异常不变。

不记录存档内容、玩家名单、房间密码、连接令牌或聊天。没有改写协议、存档转换、页面路由或错误处理逻辑。探针使用独立 Harmony ID，首次重开时安装；作用域结束后不再记录调用。额外日志和探针仍可能改变时序/JIT，因此“诊断版偶然不崩溃”本身不能作为问题已修复的证据。

## 日志

```text
user://sts2_lan_connect/diagnostics/restart/restart-<时间>-<随机标识>.jsonl
```

当前 Linux 环境对应：

```text
~/.local/share/SlayTheSpire2/sts2_lan_connect/diagnostics/restart/
```

每条带有顺序号、UTC 时间、线程号、阶段和方法名，写完立即 `Flush(true)`。每次尝试创建独立文件，不覆盖旧日志，单文件最多 512 条。`snapshot_begin` 用于区分检查对象期间的失败与原方法内部失败。正常返回会出现 `end`；若收到 `end` 后仍崩溃，则应继续检查后续异步回调，不能把它误判为这段同步流程已覆盖所有风险。

4. 不论是否崩溃，都保留此次 JSONL 和游戏 `godot.log`。首次复现后先不要连续重试或改动多项设置，以便对照。
